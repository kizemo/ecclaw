# ecclaw 宿主写操作护栏 + 直接工具面（2026-11-02）

> 阶段：第八阶段（承接 phase3g「宿主写操作」）
> 目标：把「agent 替用户操作页面」这件事从 straight-through 改成**必须用户点头**，
> 同时把 4 个写操作直接暴露成 MCP 工具（不再必须经平台包），并把宿主桥就绪状态暴露到 UI。

---

## 1. 为什么必须有护栏

上一阶段（phase3g）把 `click / scroll / interceptNext / waitForNavigation` 四个宿主写操作接通了，
但当时是**直通**的：agent 说点哪里就点哪里。这是「替用户操作页面」——下订单、点删除、发消息
都可能由 agent 自己拍板，用户完全不知情。所以接 agent 直连之前必须先补确认机制。

判断标准很简单：

| 发起方 | 是否需要确认 | 理由 |
|---|---|---|
| 用户自己在界面里点「执行页面动作」 | **不需要** | 用户已有明确意图，闸门是多余的摩擦 |
| agent 通过 MCP / 平台包触发 | **需要** | 意图来自模型，用户没参与决策 |

---

## 2. 三档策略

策略存在 `ecclaw-settings.json` 的 `hostWriteGuard` 字段（用户目录，运行时可改）：

| 模式 | 行为 | 适用场景 |
|---|---|---|
| `ask`（默认） | 渲染进程右下角弹卡片 → 用户点「允许 / 拒绝」 | 日常使用 |
| `allow` | 直接放行 | 用户明确表示信任 agent（如自动化巡检） |
| `deny` | 直接拒绝，报错回给 agent | 只读场景 / 演示 / 强制禁用 |

**只有改动页面的操作需要确认**：`click` / `scroll`。
`interceptNext`（抓网络响应）与 `waitForNavigation`（等跳转）是只读的，不打扰用户。
同理，宿主全部只读通道（`read-dom` / `extract` / `observe` / `data-query`）也不走闸门。

### 超时兜底：为什么是 40 秒而不是 60 秒

`ask` 模式下 **40 秒**没人回应 = 自动拒绝（fail-closed）。

这个数字是**被 MCP SDK 逼出来的**：openclaw 用的 `@modelcontextprotocol/sdk` 客户端请求超时是
**硬编码 60000ms**（`dist/esm/shared/protocol.js` → `DEFAULT_REQUEST_TIMEOUT_MSEC = 60000`），
超时后 agent 侧只会看到 `MCP error -32001: Request timed out`。

初版把护栏窗口也设成 60s → **两者同时到点，agent 必然先超时**：
实测 agent 连点三次 `#btn-increment`，三次都是 `-32001 Request timed out`，
页面上的按钮**根本没被点**（fixture 服务端点击计数 = 0），agent 还如实汇报「三次都在等弹窗确认时超时」。

取 40s（留 20s 余量）后重测：agent 第一次调用就拿到确认卡片 → 用户点允许 → 点击真的发生
（`dom-click` / `ok:true` / 服务端计数 1），agent 回复「已成功点击」。

> 附带的坑：护栏超时后**卡片仍留在渲染进程里**（渲染进程不知道主进程已经超时），
> 用户这时点「允许」是**空操作**（pending 已被删除，`respondApproval` 返回 false）。
> 因此窗口必须短于 MCP 超时，否则用户点的是一张「死卡片」。
>
> 更彻底的做法是把确认改成**两段式**（工具立即返回 pending 票据 + agent 轮询结果），
> 这样人的等待时间与 MCP 超时解耦 —— 列为下一轮候选。

## 3. 执行链路

```
agent ──MCP(stdio)──> host-server.mjs ──HTTP+token──> host-bridge
                                                            │ dispatch(op)
                                                            ▼
                                              host-service.hostWriteOp(op, params, 'agent')
                                                            ▼
                                              BrowserHost.runOp(op, params, { source })
                                                            │
                                              ┌─────────────┴─────────────┐
                                              ▼                           ▼
                                   requireWriteApproval()          真正执行
                                   （ask → 挂起等用户）          （CDP / DOM）
```

UI 侧（用户手动触发）：`hostRunAction(...)` → `platform-actions.runPageAction(..., 'ui')`
→ `runRunner(..., source='ui')` → `host.runOp(op, params, { source: 'ui' })` → 护栏直接放行。

### 关键实现点

- **护栏在 `runOp` 里、执行之前**（`electron/main/browser-host.ts`）：
  无论走 UI 还是 agent、走 CDP 还是 DOM，都必须过 `requireWriteApproval`。
  这样平台包子进程（`runtime.cjs` 里 `browser.click`）和 MCP 直连工具共用同一道闸。
- **发起方用 `source` 区分**（`'ui' | 'agent'`），一路透传：
  `host-service` → `platform-actions.runRunner` → `host.runOp`。
- **`click` / `scroll` 的定位信息**从 `params.target` 取：
  `click` 用 `target.selector / text / frame`；`scroll` 用 `target.target.selector / frame`
  （滚动目标是嵌套结构，因为 scroll 同时要带 `deltaY` 和目标容器）。
- **确认卡片走 IPC 推送**：主进程 `setWriteApprovalEmitter(...)` → `ipcRenderer.on('host:write-approval-request')`
  → 渲染进程渲染 `.approval-card` → 用户点按钮 → `host.respondApproval(id, approved)`。
  渲染进程重挂载后可用 `host.pendingApprovals()` 补渲染（避免卡片丢失导致永久挂起）。

## 4. 暴露到 UI 的东西

「平台包」页宿主卡片里新增一行：

- `宿主桥已就绪 :<port>` / `宿主桥未就绪` —— 状态标签（**不含 token**，token 不能进渲染进程）。
- `agent 写操作：` 下拉框（每次询问 / 直接放行 / 全部拒绝）——
  切换即调 `host.setWriteGuardMode(mode)`，策略落到 `ecclaw-settings.json`，重启后保留。

## 5. 新增的 4 个 MCP 工具

`resources/mcp/host-server.mjs` 的工具数 **8 → 12**：

| 工具 | 对应宿主 op | 是否需确认 |
|---|---|---|
| `ecclaw_click` | `click` | **是** |
| `ecclaw_scroll` | `scroll` | **是** |
| `ecclaw_intercept_next` | `intercept-next` | 否（只读） |
| `ecclaw_wait_navigation` | `wait-for-navigation` | 否（只读） |

这两个写工具的描述里明确写了「会先弹窗请用户确认，用户拒绝则失败」——让模型在选工具时就知道有闸门。

好处：agent 不必依赖任何平台包，就能直接操作宿主页面（此前只有 `ecclaw_run_action`，
必须先有包、有页面能力 id 才能写）。

## 6. 实测结果（2026-11-02，真机）

验证页：`C:/Temp/ecclaw-verify/fixture-writer.cjs`（端口 8897，`#btn-increment` 点击 +1，
`#scroll-box` 可滚动容器）。宿主页面自身是 CDP target，可直接读 `window.__ecclawCount`。

### 6.1 三档策略 + 卡片

| 场景 | 期望 | 实测 |
|---|---|---|
| `ask` 模式下点 `#btn-increment` | 弹出确认卡片 | ✅ 卡片出现，文案「点击：选择器 #btn-increment · 文本「加一」 · 页面 http://127.0.0.1:8897/」 |
| `ask` 模式下点「拒绝」 | agent 收到错误，页面无变化 | ✅ 返回 `用户拒绝了本次写操作（click）：…`，计数 1 → 1 |
| `ask` 模式下点「允许」 | 真的点下去 | ✅ 计数 1 → 2，`mode:"dom-click"` |
| `allow` 模式 | 直接执行，不弹卡片 | ✅ `ok:true`，计数 0 → 1，无卡片 |
| `deny` 模式 | 直接拒绝 | ✅ `写操作已被策略禁用（hostWriteGuard=deny）：click`，计数不变 |
| `scroll` 在 `ask` 模式下 | 同样弹确认 | ✅ 卡片文案「滚动：选择器 #scroll-box · 页面 …」，允许后 `scrollTop:200` |

### 6.2 MCP 层

- `ecclaw_click`（`allow` 档）→ `{"ok":true,"mode":"dom-click","selector":"#btn-increment"}`，`isError=false`
- `ecclaw_scroll`（`deny` 档）→ `工具执行失败：写操作已被策略禁用（hostWriteGuard=deny）：scroll`，`isError=true`
- `tools/list` 列出 12 个工具，名字与描述正确。

### 6.3 GUI 抽查（CDP 驱动真实渲染进程）

- 平台包页 `宿主桥已就绪 :62809`（端口随机，每次启动变）
- 下拉三个选项 `ask / allow / deny`，切换后 `host.writeGuardMode()` 同步变化
- `.approval-stack` 计算样式 `position:fixed; z-index:50`（卡片样式已生效）

### 6.4 agent 真调用（openclaw agent --local）

这是最关键的一条：不是我们自己的脚本点 MCP 工具，而是**真的模型**通过
`ecclaw-host__ecclaw_click` 触发写操作，用户在卡片上点「允许」。

| 轮次 | 护栏窗口 | 结果 |
|---|---|---|
| 第 1 轮（初版 60s） | 60s | ❌ agent 三次调用全部 `MCP error -32001: Request timed out`；fixture 服务端点击计数 = 0（**按钮根本没被点**） |
| 第 2 轮（改 40s） | 40s | ✅ 首次调用即弹卡片 → 点允许 → `dom-click` / `ok:true` / 服务端计数 **1**；agent 回复「已在验证页上用 ecclaw_click 成功点击 #btn-increment（dom-click 模式，返回 ok: true）」；`agent-e2e-guard3.err` 里 `MCP error` 出现 **0** 次 |

验证脚本：
- `C:/Temp/ecclaw-verify/approval-watcher.cjs` —— 轮询渲染进程，出现卡片就点「允许」（可连续应答多张卡）
- `C:/Temp/ecclaw-verify/fixture-writer.cjs` —— 服务端维护 `echoCount`（页面刷新不清零），
  用来证明「点击真的发生过」（页面内的 `window.__ecclawCount` 会被刷新归零，不可信）

### 6.5 边界

- `read-dom` 会**重新打开** URL（`hostReadDom` 里 `await h.open(target)`），
  所以用它读计数会把页面刷掉、计数归零。要验证计数变化必须直连宿主 CDP target 读
  `window.__ecclawCount`（本轮验证脚本即如此）；跨页面重载的场景用 fixture 的**服务端**计数。
- 只读 op（`intercept-next` / `wait-for-navigation`）不受护栏影响。
- 护栏超时后卡片不会自动消失（渲染进程不知情），用户点它是空操作。
