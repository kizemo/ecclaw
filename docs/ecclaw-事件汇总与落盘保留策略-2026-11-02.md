## 1. 为什么做这两块

第十阶段把宿主事件落盘了（按天 JSONL + `ecclaw_event_replay`）。落盘解决了「崩了不丢」，
但带来两个新问题：

**① agent 想问聚合问题，却只能拉原始事件。**
「哪个平台包产了多少事件、覆盖了哪几天」这类问题，用 `ecclaw_event_replay` 得把成百上千条
原始事件拉进上下文 —— 又贵又占窗口，而且模型还得自己算。

**② 「保留 14 天」挡不住磁盘被吃满。**
高频 poll 观察器一天能产几十万条事件，14 天 × 每天几十 MB 完全可能把用户磁盘写满。
原来的策略只有时间维度，没有体积维度。

这两块都不依赖用户账号，可以在第十阶段的收官 handoff 里直接排上。

## 2. 事件汇总

### 2.1 过滤语义与回放共用

关键设计：**回放与汇总走同一个扫描函数** `scanDiskEvents(filter, onEvent)`。
过滤条件（`sinceSeq` / `untilSeq` / `sinceAt` / `untilAt` / `packageId` / `pageId` / `kind`）
完全一致，回调返回 `false` 表示「够了」→ 立即停止。

这样做的收益：不会出现「回放支持过滤但汇总不支持」这类语义漂移；
以后加过滤维度只改一处。

### 2.2 汇总结果结构

「宿主事件」页新增第三个面板：

- 「历史回放」面板的提示行同步补上保留策略：`保留 14 天 · 当前 N 条 · 占用 X KB`。

## 3. 落盘保留策略细化

### 3.1 三个约束

| 常量 | 值 | 行为 |
|---|---|---|
| `RETAIN_DAYS` | 14 | 启动时 `initHostEventLog()` → `sweepDisk()` 删掉过期文件 |
| `MAX_FILE_BYTES` | 8 MB | 当天最后一个分片写满 → 新开 `events-DAY.1.jsonl` |
| `MAX_TOTAL_BYTES` | 256 MB | 目录总体积超限 → 从**最老的一天**开始整日删除 |
| `TRIM_CHECK_EVERY` | 200 | 每写 200 条才检查一次总体积（避免每条都 stat 整个目录） |

### 3.2 分片命名与解析

```
events-2026-11-02.jsonl        ← 当天第 0 片
events-2026-11-02.1.jsonl      ← 当天第 1 片
events-2026-11-02.2.jsonl      ← 当天第 2 片
```

`LOG_FILE_RE = /^events-(\d{4}-\d{2}-\d{2})(?:\.(\d+))?\.jsonl$/` 统一解析，
`listLogFiles()` 按「天 + 分片序号」排序 → 跨分片的回放与汇总仍然连续、有序。

### 3.3 写入路径

```
appendToDisk(event)
  ├─ 找当天最后一个分片
  ├─ 该分片体积 + 本行长度 > 8MB ? → 新开 part+1
  └─ appendFileSync
```

`TRIM_CHECK_EVERY` 计数到顶时调 `trimToSize()`（整日淘汰最老的一天）。

## 5. 本轮踩坑

1. **上下文预算**：上一会话在 ctx 160K 硬闸门下被拦，`Read` 被拒 → 连整文件 `Write` 也被拒
   （Write 要求「先 Read」）→ 同一文件形成死锁。
   **教训：大改动前先 Read 目标文件，别攒到最后**；批量 Edit 也要留一个 Read 预算。
2. **同 message 内多文件 Edit 是允许的**（types.ts / host-service.ts / preload / index.ts /
   host-server.mjs 全部一次成功），但**跨会话没 Read 过的文件会直接被拒**。
3. **验证脚本会污染真实日志目录**：8MB 滚动测试直接写在用户数据目录里，测完必须清理，
   否则 `event-log-info.total` 被虚高、后续回归判断失真。
