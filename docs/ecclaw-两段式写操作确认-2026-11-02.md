# ecclaw 第九阶段 · 两段式写操作确认

> 日期：2026-11-02 ｜ 基线：`handoff-ecclaw-phase3h-2026-11-02.md`（第八阶段：写操作护栏）
> 状态：MCP 工具层 + 拒绝路径 + 真 agent 链路已全绿（证据见 §6）

---

## 1. 这一阶段解决什么问题

第八阶段的写操作护栏是**阻塞式**的：agent 调 `ecclaw_click` → 宿主弹确认卡片 → MCP 调用**一直挂着**
等用户点「允许」→ 用户点了才返回结果。

两个硬伤：

1. **人的等待时间被 MCP 的 60s 硬超时夹住**。MCP SDK 客户端请求超时硬编码
   `DEFAULT_REQUEST_TIMEOUT_MSEC = 60000`，护栏窗口只能取 40s（留 20s 余量）。
   用户离开界面、或者只是回消息慢一点，操作就自动拒绝了。
2. **agent 与人被绑在同一个调用栈上**。等批准的这段时间里 agent 什么都干不了，
   也拿不到「被拒绝」这种明确结论（超时只给 `MCP error -32001: Request timed out`）。

第九阶段改成**两段式**：写操作工具**立即**返回一张票据，真正的执行推迟到用户批准之后，
agent 拿着票据号去轮询结果。人的等待时间与 MCP 的 60s 超时**彻底解耦**。

## 2. 契约

### 2.1 写操作工具的返回

`ecclaw_click` / `ecclaw_scroll`：

```jsonc
// 需要用户确认（护栏 ask 档）
{ "status": "pending", "approvalId": "w-mvyibhjs-1" }

// 无需确认（allow 档 / 只读）
{ "status": "executed", "result": { "ok": true, "mode": "dom-click", "selector": "#btn-increment" } }
```

### 2.2 轮询工具（第 13 个 MCP 工具）

`ecclaw_approval_status(approvalId)` → 票据当前状态：

```jsonc
{
  "id": "w-mvyibhjs-1",
  "op": "click",
  "summary": "点击：选择器 #btn-increment · 页面 http://127.0.0.1:8897/",
  "status": "executed",          // pending | approved | executed | failed | rejected | timeout
  "result": { "ok": true, "mode": "dom-click" },
  "error": "用户拒绝了本次写操作",  // 仅失败类状态
  "createdAt": "2026-11-02T00:14:41.560Z",
  "updatedAt": "2026-11-02T00:14:41.919Z"
}
```

### 2.3 状态机

```
        ┌──────────► rejected  （用户拒绝，绝不执行）
pending ┤
        ├──────────► timeout   （超时未确认，fail-closed，绝不执行）
        │
        └──────────► approved ──► executed（result）  /  failed（error）
```

## 3. 实现落点

| 文件 | 改动 |
|---|---|
| `electron/main/write-guard.ts` | 重写：票据存储（op+params+结果）、状态机、两段式 `requestWriteApproval`、阻塞式 `runWithWriteApproval`、结果查询 `approvalStatus` |
| `electron/main/browser-host.ts` | `runOp(op, params, { mode })`：`blocking`（平台包 runner）/ `deferred`（MCP 直连）两种等待形态 |
| `electron/main/host-service.ts` | `hostWriteOp` 走 `mode: 'deferred'` |
| `electron/main/host-bridge.ts` | 新增 op `approval-status` |
| `electron/main/index.ts` | 新增 `setWriteApprovalUpdateEmitter` 推送 + IPC `host:write-approval-status` |
| `electron/preload/index.ts` | 新增 `approvalStatus` / `onWriteApprovalUpdate` |
| `electron/shared/types.ts` | `WriteApprovalStatus` / `WriteApproval` 票据类型 |
| `resources/mcp/host-server.mjs` | 工具 12 → **13**（`ecclaw_approval_status`），click/scroll 描述改写 |
| `src/App.tsx` / `src/styles.css` | 卡片显示票据状态；终态卡片 12s 后自动收起 |

### 关键设计点

- **闸门仍只有一道**：`BrowserHost.runOp` 里分叉的是「等待形态」，不是「要不要审批」。
  平台包 runner（包内 `await browser.click()`）必须拿到执行结果，所以走 `blocking`；
  MCP 直连工具走 `deferred`。两条路径都过同一套 `MUTATING_OPS` / 策略判定。
- **执行体存在票据里**：`resolveWriteApproval` 批准后**在主进程后台**跑 runner，
  结果写回票据。agent 轮询拿到的就是这次真实执行的结果。
- **两个超时**：
  - `BLOCKING_TIMEOUT_MS = 40s` —— 阻塞式窗口，必须**明显 < MCP 的 60s**（老坑）。
  - `PENDING_TIMEOUT_MS = 10min` —— 两段式票据的存活窗口，已与 MCP 超时解耦，可以给用户长时间思考。
- **fail-closed**：拒绝 / 超时的票据**绝不执行**；`deny` 档直接抛错。
- **终态票据保留 30 分钟后清理**，避免内存无限增长。

## 4. 渲染进程的卡片

- pending：显示「拒绝 / 允许」按钮。
- 已答复：按钮消失，就地显示状态（已允许，正在执行 / 已执行 / 执行失败 / 已拒绝 / 已超时）。
- 状态由主进程推送（`host:write-approval-update`），渲染进程重挂载后用 `pendingApprovals()` 补渲染。
- 终态卡片 12 秒后自动收起（保留最近 8 张）。

---

## 5. 已知边界

- **平台包内部的动作仍是阻塞式**（40s 窗口）。包内代码 `await browser.click()` 期待的是执行结果，
  塞票据进去会破坏包语义。要把包内点击也两段式化，需要改 dabi 的包契约 —— 超出本阶段范围。
- 票据是**单次**的，不支持复用同一个 approvalId 提交多个操作。
- 票据只在主进程内存里，重启 Electron 就没了（agent 会拿到 null）。

## 8. 护栏粒度：站点白名单（一次授权一批）

两段式解决「人等不及」，站点白名单解决「一次只授权一个动作」。

### 契约

用户点卡片上的第三个按钮「允许并信任本页面」→ 主进程把**当前页面的域名**写进
`ecclaw-settings.json` 的 `hostWriteGuardAllowlist`（字符串数组）→ 该站点之后的写操作
**直接放行**，不再逐次弹卡。

- 匹配规则：精确匹配，或后缀匹配（`.taobao.com` 覆盖 `shop.taobao.com`）。
- 白名单在 `ask` 判定**之前**检查；`allow` 档仍然全放行，`deny` 档仍然全拒。
- 只影响「来源 = agent」的操作；用户在界面里自己点的不走这道闸。

## 9. 踩坑记录

1. **MCP SDK 客户端请求超时硬编码 60000ms**（`DEFAULT_REQUEST_TIMEOUT_MSEC`）。
   阻塞型工具总耗时必须明显 < 60s；两段式是根治办法，不是把窗口调大。
2. **测试脚本也会骗人**：看门狗原来只取 `.approval-card` 的**第一张**，
   而上一轮测试留下的「已执行」卡片还在浮层里 → 点不到新卡片的「拒绝」，
   看起来像「拒绝路径坏了」。修法：只认**还带按钮**（pending）的卡片。
3. **Electron 用后台任务方式启动会被回收**（进程静默消失、端口释放、日志无崩溃信息）。
   修法：`powershell Start-Process` 脱离控制台启动。
4. **fixture 进程也会被回收** → 验证前先 `netstat` 确认 8897/8898 在监听，必要时重启。
