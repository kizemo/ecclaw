# ecclaw 宿主写操作（2026-11-02）

> 第七阶段：把 dabi 平台包里依赖的**写操作**补齐 ——
> `browser.click` / `browser.scroll` / `browser.interceptNext` / `browser.waitForNavigation`
> （此前这四个在最小 SDK 里是 `unsupported(...)` 占位，抛「ecclaw 宿主暂不支持」）。

## 1. 契约（来自真实 dabi 包的实际用法）

在 `platform-packages/`（taobao / wxt / amazon / douyin / doudian-compass …）里实测到的签名：

| SDK 调用 | 语义 | 返回 |
|---|---|---|
| `browser.click({ selector, text?, frame? }, { humanize?, timeoutMs? })` | 点击命中的元素（`text` 在 selector 命中的多个元素里再筛） | `{ok, mode}` |
| `browser.scroll({ deltaY?, target?: { selector, frame? }, humanize? }, { timeoutMs? })` | 无 target 滚窗口；有 target 滚该容器（无 deltaY 则滚进可视区） | `{ok, mode}` |
| `browser.interceptNext(pattern, { timeoutMs })` | 等「下一次」匹配 glob 的请求，回传响应体 | `{ url, method, status, body, base64Encoded }` |
| `browser.waitForNavigation({ timeoutMs })` | 等下一次页面跳转（先 arm，再触发） | `{ url }` |

`interceptNext` 的 pattern 是 glob（`*` 通配），真实例子：`*mtop.taobao.shop*`；
doudian-compass 的 `videoResponsePattern(...)` 也是同类。

## 2. 实现分层

```
平台包 runtime.cjs
  → 最小 SDK stub（electron/main/platform-actions.ts 的 RUNNER_SCRIPT）
      browser.click/scroll/interceptNext/waitForNavigation → process.send({type:'op', op, params})
  → 主进程 runRunner 分发 → host.runOp(op, params)
  → BrowserHost（electron/main/browser-host.ts）
      click / scroll / interceptNext / waitForNavigation
```

- **runner 侧**：`browser.*` 不再是 `unsupported(...)`，改成 `rpcOp(op, params, options)`；
  子进程 → 主进程新增 `type:'op'` 消息（与既有 `type:'eval'` 同一条 pending 表）。
- **主进程侧**：`BrowserHost.runOp()` 按 op 分发到四个方法；
  `runPageAction` 之前会先 `enableNetworkCapture()`（`interceptNext` 依赖网络捕获）。
- **拦截器**：宿主维护 `interceptors` 列表，`Network.loadingFinished` 时先匹配拦截器
  （glob → 正则），命中则 `Network.getResponseBody` 取体并 resolve 回执。

## 3. 两条执行路径（重要）

| 宿主页面状态 | 点击 | 滚动 |
|---|---|---|
| **可见**（渲染进程给了真实占位盒矩形） | CDP `Input.dispatchMouseEvent`（mouseMoved → mousePressed → mouseReleased） | CDP `Input.synthesizeScrollGesture` |
| **隐藏**（viewport 为 null） | DOM `el.click()` | DOM `el.scrollBy(0, delta)` / `window.scrollBy` |

原因见 §4 的坑 1、2。回执里带 `mode`（`cdp-click` / `dom-click` / `gesture` / `dom-scroll`），便于判断走了哪条路。

## 4. 踩过的坑（别再踩）

1. **隐藏的 widget 不收 CDP 输入事件**：`setVisible(false)` 的 WebContentsView 里
   `Input.dispatchMouseEvent` 会被静默丢弃 —— 事件发出去了，页面毫无反应。
   → 隐藏态必须走 DOM 事件。
2. **隐藏不能收成 0×0**：view 宽高为 0 时页面布局宽度也是 0，
   `getBoundingClientRect()` 全是 0，点击坐标无从计算。
   → 隐藏时保持 `1280×800` 的布局尺寸 + `setVisible(false)`（实测布局正确、坐标可用）。
3. **挪到画面外也不行**：把 view 放到 `x = -1280` 时，渲染进程的视口宽度被裁成 0，
   元素坐标又变成 ~0。**只有「有尺寸 + setVisible(false)」这一种隐藏方式可用**。
4. **`Input.dispatchMouseEvent{mouseWheel}` 不产生滚动**：实测 scrollTop 恒为 0。
   → 改用 `Input.synthesizeScrollGesture`（`yDistance` 取负才是向下滚），
   并且**滚完要校验 scrollTop 是否真的变了**，没变就回退 DOM 滚动。
5. **`interceptNext` 登记前不能 await**：包内常见写法是
   `const t = browser.interceptNext(p); ...触发请求...; await t`。
   若登记拦截器前有任何 await，随后的页面请求会抢先发出、拦截器抓不到。
   → 拦截器登记必须与收到 RPC 的同一拍完成（`ensureDebugger()` 是同步的，`Network.enable` 丢后台）。
6. **`did-navigate` 会误触发**：arm 等待跳转时页面可能还在加载完成中，
   同 URL 的导航要忽略（只认 URL 变化）。

## 5. 验证

示例包 `resources/platform-packages/ecclaw-writer-demo`（真实包同形），
验证页 `C:/Temp/ecclaw-verify/fixture-writer.cjs`（端口 **8897**，注意 8899 已被别的服务占用）。

```bash
# fixture（8897）
cd C:/Temp/ecclaw-verify && node fixture-writer.cjs

# 直接打宿主桥
node C:/Temp/ecclaw-verify/bridge-rpc.cjs action \
  '{"packageId":"ecclaw-writer-demo","capability":"ecclaw-writer-demo.click","url":"http://127.0.0.1:8897/writer"}'

# 让宿主页面可见（走真实鼠标/手势路径）
node C:/Temp/ecclaw-verify/cdp-viewport.cjs 0 0 900 600
```

实测（2026-11-02，可见 / 隐藏两种状态各跑一遍，8/8 全绿）：

| 动作 | 可见 | 隐藏 |
|---|---|---|
| click | `mode:"cdp-click"`，计数 `0 → 1` | `mode:"dom-click"`，计数 `0 → 1` |
| scroll | `mode:"gesture"`，`scrollTop: 300`（页面未动） | `mode:"dom-scroll"`，`scrollTop: 300` |
| intercept | 抓到 `http://127.0.0.1:8897/api/writer/echo?from=package`，body 为真实 JSON | 同左 |
| navigate | 拿到 `http://127.0.0.1:8897/writer-target` | 同左 |

MCP 层同样通：`tools/call ecclaw_run_action{packageId:"ecclaw-writer-demo",…}` → `ok:true`。
